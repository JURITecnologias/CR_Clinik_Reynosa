## 2. System in one pass

This is an electronic medical record and clinic operations application. The active custom workflows cover patients and medical history; doctors and schedules; appointments; consultations and vital signs; prescriptions; medical services and medicines catalogs; clinical orders, consumable master data and kits; notifications; dashboards and medical reports. The repository also contains many Dream EMR template/demo PHP pages; a page's existence alone does not prove an implemented workflow. Confirm its API calls and routes before documenting it as live.

Request path: browser loads a PHP page from `front/src/`, composed through `front/partials/main.php`; feature JavaScript calls the Laravel JSON API under `/api`; Laravel route middleware authenticates and checks role/permission; controller reads/writes Eloquent models in MySQL; JSON returns to browser. The frontend is server-rendered PHP plus jQuery/vanilla JS, not a SPA framework. Sources: `front/partials/main.php`, `front/assets/js/app/config.js`, `backend/api-consulmdregister/app/Providers/RouteServiceProvider.php`.

Core relationships (navigation shorthand; inspect migrations for actual foreign-key enforcement): `User ↔ Role ↔ Permissions`; `User → InformacionDoctor → HorarioDoctor`; `Paciente → PacienteHistorialMedico`; `Paciente + InformacionDoctor → Consulta → SignosVitales`; `Paciente + optional doctor + optional Consulta → CitaPaciente`; `Consulta → RecetaMedica`; `Consulta → OrdenClinica → OrdenClinicaConsumo → Consumible OR KitConsumible → KitPredefinido`; `Consumible → MovimientoConsumo`; `User ↔ Notificacion` through `notificacion_usuario`. The models and migrations define exact cardinality and optionality; this shorthand is a navigation aid.

## 4. Authentication and authorization contract

`POST /api/login` checks email/password and returns user, roles, permissions, and a Base64 encoding of `name:password` called `token`. Browser JavaScript stores that in `sessionStorage`, sends `Authorization: Basic <token>`, and passes it as `?t=` to `front/src/auth-signin-basic.php`. That PHP page sets `$_SESSION['loggedin']=true` before validating token or profile response; `front/partials/session.php` uses this separate flag as a page gate. Therefore a PHP page's gate is not evidence of API authorization; the API still applies Basic middleware. The Base64 value is reversible credentials, not an opaque access token; treat it as sensitive and do not log, index, or put it in examples. Sources: `AuthController.php`, `front/assets/js/app/login.js`, `front/assets/js/app/config.js`, `front/src/auth-signin-basic.php`, `front/partials/session.php`.

`basic.auth` decodes credentials and attaches `authenticated_user`; `check.role` and `check.permission` read that user's roles and their permissions. A pipe-separated gate means **any** listed role/permission. Laravel's pipeline splits middleware arguments at commas before invoking `handle`. Thus a consumable master-data gate spelled `check.permission:escribir,modificar` passes `escribir` as the first argument; this custom `CheckPermission::handle()` accepts only that argument and ignores the second. It requires `escribir`, not either permission. `auth:sanctum` appears only on `/api/user`. Sources: `app/Http/Middleware/BasicAuthMiddleware.php`, `CheckRole.php`, `CheckPermission.php`, `routes/api.php`, installed Laravel `vendor/laravel/framework/src/Illuminate/Pipeline/Pipeline.php`.

The Basic middleware attaches the user to the request but does not set Laravel's `Auth` guard. Code using `Auth::id()` must not assume it receives the Basic-authenticated user. Source: `app/Http/Middleware/BasicAuthMiddleware.php`.

Seeded roles: `Main Admin`, `Admon`, `Doctor`, `Enfermera`; seeded permissions: `ver`, `escribir`, `modificar`, `borrar`. Admin and Doctor roles receive all four; Enfermera receives `ver` only in the role-permission seeder. Some routes refer to `Ventas`, which is not in the default roles seeder. Route gates, not a role-name assumption, govern each operation. Sources: `database/seeders/RolesTableSeeder.php`, `PermissionsTableSeeder.php`, `RolePermissionSeeder.php`, `routes/api.php`.

Representative route gates (recheck `backend/api-consulmdregister/routes/api.php` for every endpoint):

| Operation | Declared gate |
| --- | --- |
| Patient read / create-update / delete | `ver` + listed care/admin roles / `modificar|escribir` + listed roles / `borrar` + Main Admin, Admon, Doctor |
| Consultation read / create-update / delete-restore | `ver` / Doctor + `escribir` / Main Admin, Admon, Doctor + `borrar` |
| Appointment read / create-update / delete | `ver` / care/admin roles + `modificar|escribir|ver` / Main Admin, Admon, Doctor + `borrar` |
| Clinical order read / create-update-state-consumption / delete | `ver` / Main Admin, Admon, Doctor, Enfermera with no permission check / same roles + `borrar` |
| Consumable/category/kit master data read / write | `ver` / Main Admin or Admon + effective `escribir` requirement from the comma-form gate |
| Queued report routes | Main Admin or Admon + `ver` |

## 5. Domain model and workflow rules

### Patient and history

`pacientes` stores identity/contact fields including CURP and `numero_seguro`, timestamps, soft delete. `Paciente::historialMedico()` is one-to-many; history rows hold demographics plus chronic diseases, allergies, medicines, family history, habits, mental health and notes. `PacienteHistorialMedicoController` creates/updates using model fillable data and has no explicit request validation in those methods. Patient create checks exact `nombre` + `apellido` + `fecha_nacimiento` for an existing patient and returns 409 on a match; update uses mass-assigned model fillable fields. Search filters full name, phone, email, CURP, insurance number, with pagination. Do not claim a database uniqueness constraint or robust identity matching. Sources: patient/history migrations, `app/Models/Paciente.php`, `app/Models/PacienteHistorialMedico.php`, `PacienteController.php`, `PacienteHistorialMedicoController.php`.

### Doctor, schedule, appointment

`informacion_doctor` links a doctor profile to a user; `horarios_doctores` records weekday, start/end time and active state. Schedule creation rejects overlapping ranges for the same doctor/day; schedule update does not repeat that overlap check. `citas_pacientes` links a patient, optional doctor, optional consultation, date/time, `atendio_cita`, notes, soft delete. Appointment create/update validate referenced IDs and date; search filters patient, doctor, consultation, date and patient name. The appointment controller does not check for overlapping appointments or automatically create a consultation. Sources: `CitaPacienteController.php`, `app/Models/CitaPaciente.php`, schedule/appointment migrations, `HorariosDoctoresController.php`.

The consultation page's `GuardarConsulta` flow can update an existing appointment or create one when the separate appointment form fields `frm_cita_fecha` and `frm_cita_hora` have values. This is frontend orchestration, not an appointment-controller invariant. Source: `front/assets/js/app/consultas.js`.

### Consultation and vital signs

`consultas` belongs to patient and doctor; stores date, complaint/symptoms/diagnosis/instructions, JSON medicines/services, `motivos_consulta`, status and `fuera_de_horario`, with soft delete. Status validation permits `abierta`, `enfermeria`, `completada`. `Consulta::signosVitales()` is one-to-one. Create checks patient and doctor existence, validates selected fields, derives local day/time from request `create_at`, checks an active matching doctor schedule, sets `fuera_de_horario`, creates critical notifications for Main Admin and Admon if outside the schedule, and creates associated vital signs. The current new-consultation JavaScript sends `fecha_consulta` but no `create_at`; do not assume the chosen consultation date drives that schedule check. Update may modify clinical fields and existing vital signs; delete/restore use soft deletes. This sequence is not wrapped in an explicit database transaction. In the browser's `ImprimirReceta` mutating branch, `front/assets/js/app/consultas.js` proceeds from `abierta`, creates a prescription, then sets `completada` or `enfermeria` if selected services have category `enfermeria`, and may create a clinical order. For other statuses, that function attempts to download an existing PDF. These are UI steps across requests, not server-enforced status transitions. Sources: consultation and vital-sign migrations, `app/Models/Consulta.php`, `ConsultasController.php`, `NotificacionService.php`, `front/assets/js/app/consultas.js`.

The merged `main` adds `front/src/nueva-consulta-emergencia.php` and a `ConsultasController::storeEmergencia()` method that evaluates the doctor schedule using `fecha_consulta`. The browser first posts to `/api/consultas/emergencia` and tries `/api/consultas` after an unsuccessful first attempt; the catch path can continue after errors beyond 404/405. `routes/api.php` does not register the emergency endpoint in this snapshot. Treat the emergency-specific controller method as unreachable through the current API and verify fallback behavior before changing this flow. Sources: `front/assets/js/app/consultas.js`, `front/src/nueva-consulta-emergencia.php`, `ConsultasController.php`, `routes/api.php`.

### Prescription, catalogs, clinical order

`receta_medica`/`RecetaMedicaController` associate prescriptions with consultations. Prescription creation allocates `folio_receta`, generates a UUID, signs a hash of UUID/patient name/birth date with a local OpenSSL private key at `storage/app/keys/private.pem`, and saves the Base64 signature. The key is a local prerequisite and must not be indexed or copied into memory. `PdfRecetaController` renders a PDF with an optional doctor signature image, QR linking to `recetas/verificacion?uuid=...`, and a hardcoded `DEMO DE SISTEMA` watermark. No matching verification route exists in `routes/web.php` or `routes/api.php` at this snapshot; do not claim working public verification. Medicines and medical services have separate catalogs and routes. An order (`ordenes_clinicas`) stores patient, consultation, doctor and creating user references, UUID, configured sequential `folio_orden`, requested services JSON, date, observations, optional attending user, and state `pendiente | en_proceso | cancelada | completada`. The merged controller permits nullable `consulta_id` and `doctor_id` on creation, while the existing migration declares both foreign IDs non-nullable; validate the effective schema before relying on optional values. Order creation reads/increments `configuracion_sistema.folio_orden_clinica` without an explicit transaction or lock. Consumption rows (`ordenes_clinicas_consumos`) reference an individual consumable or a kit item, quantity and user. A `kit_id` in that row references `kits_consumibles`, whose `kit` points to `kits_predefinidos`; do not collapse those IDs. Sources: `RecetaMedicaController.php`, `PdfRecetaController.php`, corresponding migrations/models/controllers, `OrdenClinicaController.php`, `OrdenClinicaConsumoController.php`.

### Consumable inventory

`consumibles` has UUID/internal code, category, unit, current/minimum stock, average price/cost, active flag and soft delete. `kits_predefinidos` group consumables through `kits_consumibles` with a quantity pivot. `ConsumibleController` exposes catalog create/read/update/delete and accepts `stock_actual` directly on create/update. A `MovimientoConsumo` model and 2025 `movimientos_consumos` migration exist, but this `main` snapshot has no registered movement API, movement service, or inventory movement UI. Capturing a clinical-order consumption row does not itself change stock. Sources: `ConsumibleController.php`, `app/Models/MovimientoConsumo.php`, `database/migrations/2025_10_14_012317_add_table_movimientos_consumos.php`, `routes/api.php`.

### Notifications and reports

`NotificacionService` creates global, role-targeted, and individual notifications. User-specific reads and mark-read use `notificacion_usuario` pivot with `leida`/`leida_en`; global notifications create read-pivot rows when marked read. The `/notificaciones/no-leidas` and global list paths also use legacy row-level `leida`, so endpoints are not interchangeable. Dashboard routes aggregate recent patient, appointment, consultation and order counts/lists. `ReportsController` exposes service, nursing, emergency and outpatient metrics plus a medical XLSX report. Report dispatch creates a `reports` row (`pending`), launches `GenerateMedicalReportJob`, then records `completed`/`failed` and file path; download requires completed. `ExcelReporteMedicoService` loads the tracked `storage/app/templates/informe_medico_template.xlsx`; the job writes a timestamped file under `storage/app/public/`. Under declared sync queue settings this work runs during the request. Sources: `app/Providers/NotificacionService.php`, `NotificacionController.php`, `DashboardController.php`, `ReportsController.php`, `app/Services/ExcelReporteMedicoService.php`, `app/Jobs/GenerateMedicalReportJob.php`, report migration, `routes/api.php`.

`ReportServiceProvider` contains MySQL-specific reporting SQL, including `JSON_TABLE`, `JSON_CONTAINS`, and `TIMESTAMPDIFF`; an alternate database must support or replace those queries. Source: `app/Services/ReportServiceProvider.php`.

## 8. Current edge cases and verification gaps

1. **Clinical-order stock boundary:** saved `ordenes_clinicas_consumos` rows do not post stock movements in this branch. No registered order endpoint invokes a movement service for those rows; do not infer that completing an order decrements inventory. Verify any future posting endpoint for whole-order transactions, idempotency, and sufficient stock.
2. **Movement feature boundary:** `MovimientoConsumo` and its database table exist, but `main` has no movement controller/service/routes or movement pages. The separate `marco/modulo-inventario` branch contains work in this area and needs independent review before merging.
3. **Auth and data exposure:** Basic credentials travel in browser storage and URL query at login; some APIs return patient/clinical data. Review access and logs before changing auth or exposing endpoints. The CORS config permits `*` origins and methods/headers; verify deployed behavior before claiming a policy.
4. **Time and consistency:** effective Laravel timezone is UTC in `config/app.php`; consultation schedule matching uses explicit Mexico City conversion of request `create_at`, which the current new-consultation JS does not send. Appointment conflict checks are absent in its controller. Order folio allocation is not locked. Do not infer global time normalization or concurrency safety.
5. **Routes versus seeds:** consumable/category/kit comma-form gates effectively test `escribir` only; `Ventas` occurs in route gates but not default role seeding. Some order mutations have a role check but no permission check. Check exact gate before modifying a workflow.
6. **Test coverage:** repository has Laravel example PHPUnit tests, not meaningful domain tests. `front/composer.json` `test`/`test:quick` scripts run PHPStan; `test` also generates a baseline. Verify changes with targeted checks; do not report the clinical workflows as test-covered.
7. **Unknowns:** no production DB contents, deployment state, external integrations, or user acceptance evidence were inspected. Validate those separately when a task depends on them.
8. **Merged-main differences:** the emergency consultation UI calls an unregistered specialized route before falling back to ordinary consultation creation; the specialized controller method is not reachable through `routes/api.php`. Order creation accepts nullable doctor/consultation IDs despite non-nullable migration columns. Confirm route and schema before treating either as a working contract.
